# 时间戳与逐点更新、扫描发布频率

2026-10-11。当前恢复逐点 Point-LIO point→map 更新，默认在扫描末点输出。
下面保留旧录包的时间审计及相邻窗口方案的失败记录；本轮新实机见 [双雷达与单雷达对比](双雷达与单雷达对比.md)。

## 时间从哪里来

驱动在 `pub_handler.cpp` 中读取设备PTP时间，两路统一减去本机配置的37秒，将TAI转为UTC。
严格PTP模式下，未同步包在入队前丢弃，不以主机收包时间替代。

- 点云 `header.stamp`：一帧中第一个原始点的采样时间。
- 点字段 `timestamp`：相对于该header的纳秒偏移，虽为FLOAT64，数值单位仍是纳秒。
- 激光点时间：`header.sec + header.nanosec * 1e-9 + timestamp * 1e-9`。
- IMU时间：原始IMU的header，沿用设备时间，不加点云header或第二次UTC偏移。
- 当前动态TF、Odometry与注册点云：扫描中最后有效点的采样时刻；选用逐点发布时，
  Odometry/TF 为每个跟踪点的实际采样时刻，注册点云仍在扫描完成后发布。
- 已停用的 10 ms 窗口模型曾以每窗最晚有效输入点作为时间戳，不能混作当前输出定义。
- TF静态安装关系使用 `/tf_static`，它不承担运动采样频率。

标签/有限性筛选可能使最晚有效输入点早于设备帧末，不能将这段差直接当作同步误差。
动态TF使用状态实际对应的时刻，不能用 `now()` 给旧状态盖上新时间戳。

## IMU短长周期交替仍需核实

IMU的整数纳秒header并非严格每5ms一次，两个录包都存在强烈的短长交替：

| 项目 | 静止包 | 云台旋转包 |
| --- | ---: | ---: |
| 短间隔中位数 | 4.27433 ms | 4.27090 ms |
| 长间隔中位数 | 5.733645 ms | 5.73922 ms |
| 相邻间隔相关系数 | −0.98141 | −0.97916 |
| 短长交替比例 | 99.993% | 99.930% |
| 两步间隔中位数 | 10.0001 ms | 10.0001 ms |
| 去线性趋势后相对200Hz网格的相位标准差 | 约0.371 ms | 约0.371 ms |

主机接收间隔也呈同样交替模式，与header间隔高度相关。这不是百纳秒浮点舍入，
也不像普通随机接收抖动。当前驱动直接复制设备IMU时间；录包未保存设备采样触发信号，
无法由此判定header对应真实采样时刻、打包时刻或上报时刻。

PTP对齐设备与主机时钟，不能单独证明雷达与IMU的物理采样相位准确。
后续应核对设备协议/固件的IMU时间戳语义，并在需要时结合原始包和独立运动参考估计时差。
在证实前保留原始header，不能强行改成均匀5ms网格，也不能把接收时间代替设备时间。

## 浮点精度与旧发布调度

当前约1.79×10⁹的纪元秒存为double时，相邻可表示数约相差238ns。
两包约4900万点按当前解码公式回转为ROS整数时间的最大误差为365ns，
没有合并任何相邻真实采样时刻，也没有产生浮点时间回退。
这说明存在百纳秒舍入，不能将它解释为毫秒级时差。

旧录包另有一种发布时刻差异：静止122/1432帧、旋转112/994帧输出的时间
精确对应较晚IMU，而非扫描最后有效点；最大比有效末点晚3.836ms与12.954ms。
旧主循环处理完共同时间水位以内的队列后再发布，后面的IMU会推进状态和输出时刻。
这是调度及扫描输出定义的差异，不代表PTP发生偏移，也不说明旧TF时间与其状态不一致。

改模前的修复版本曾将每个 `scan_end` 作为独立事件，在其自己的时刻完成地图插入和帧末发布。
该旧模型回放414帧原始点云，初始化后404帧有输出：

- 404组Odometry、TF、注册点云的时间戳逐条完全一致。
- 全部输出匹配各自最后有效点，整数差为−320～304ns，没有毫秒级偏差。
- 输出没有倒退或重复，传感器时间轴上的扫描周期中位数为99.84ms。

该短段采用2倍播放，发布到主机的速率因此也提高；它验证时间对应关系，不代表实机输出频率。
这种加速回放下旁路订阅到的原始/转换IMU计数不一致，不能据此宣称整个数据流无丢样。
正常速度检查另保存在 `current_timestamp_normal_speed.json`：127帧原始/转换点云stamp一致，
117组Odom/TF stamp一致；原始IMU旁路订阅2549条、转换订阅2553条。
原始流采用best_effort，不同订阅路径的计数不能单独判定哪个环节丢样或是否改写时间。

## 当前逐点更新与输出

每点先推进状态和协方差，再进行激光点到历史地图平面的标量 EKF 更新；IMU 按自身
时间插入同一时间序列。点云与 IMU 不需要具有相同 header，也不应强行改成统一采样网格。
默认 `publish_odometry_without_downsample=false`，扫描末点统一发布 Odom/TF/注册点云。
设为 true 可额外逐跟踪点发布 Odom/TF，但仍随驱动整帧交付而成批发出，不能称低延迟实时输出。

主滤波只处理激光和 IMU 共同覆盖的时间。Sentry PLIO 另有独立 IMU 预测输出，
在扫描校正后重放较新缓存 IMU，以定时器发布约100Hz预测状态；LY 当前没有该独立路径。
不能用重复位姿并盖 `now()` 的办法模拟高频预测。默认约10Hz是扫描发布频率，
不是激光 EKF 更新频率，也不是每帧只使用一个点。
